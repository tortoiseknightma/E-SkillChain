01 · Executive brief

我真正解决的，不是“把几个数据集拼起来”

核心难点是建立一条可审计的转译链：论文业务意图 → 可执行能力 → 所需监督信号 → 合适的公开数据 → 有事实依据的交互轨迹 → 人工批准的评测样本。每一层都只承担自己有资格承担的责任。

贡献 01 · 任务建模

把模糊的业务意图拆成有输入、工具、gold 和输出契约的能力。

贡献 02 · 数据工程

不按数据集名选数据，而按“评测所需监督信号”组合数据源。

贡献 03 · 人机协作

Codex 负责受控组合与改写，人类保留事实、边界与接收权。

一句话定位：我构建的不是一个“合成问句集合”，而是一套以真实公开资产为事实锚点、以冻结 TaskSpec 为语义锚点、以 Codex 为受约束合成器、以人工审批为最终门禁的电商视觉 Agent 轨迹生产线。
简历与面试的声明边界 本项目是公开数据上的机制级复现：包含真实商品/文档/物种/菜品图像、真实模型调用与真实工具执行，但不声称拥有论文中的生产查询、企业内部数据、线上用户分布或论文绝对分数。
02 · From paper to executable tasks

第一步：先把论文的“意图”变成可执行任务

SkillChain 论文把图像电商助手的请求归为五类。它们是业务层的意图，不直接等同于数据集标签。我的第一步不是搜索数据集，而是追问：这个意图需要系统完成什么动作，什么证据才能判断它做对了？

Multi-Product识别场景中的多个商品
Divergent Recommendation按风格与约束推荐
Encyclopedia识别视觉主体并解释
Utility Assistance调用专用工具解决场景任务

为什么是 5 → 6

Utility 是工具族，不是单一标签

论文的 Utility 同时包含健康、菜谱、文档等子场景。第一版只实现最容易以公开数据构造可靠 gold 的两类：文档读取与菜谱指导。二者需要的工具和正确性判据完全不同，因此不能混成一个数据任务。

为什么不能照搬论文数据

论文的生产查询不可获得

论文实验使用生产查询和内部链路；本项目没有这些数据。因此我复现的是“Skill 自进化的机制”和任务结构，而不是线上流量分布。公开数据负责提供可复核事实，合成层负责恢复交互形态。

面试关键词这一步叫 operationalization：把论文概念操作化为可以构造、运行和评分的任务定义。它决定后续数据搜索不会被“看起来相关”的数据集带偏。
03 · Supervision-first selection

第二步：按监督信号找数据，而不是按名字找数据

一个数据集“有商品图片”不代表它能评测商品检索；“有食物类别”不代表它能验证菜谱事实。每个候选数据源都要依次通过五个问题。

系统必须输出什么？商品卡、多个物体、推荐理由、知识答案、字段或步骤。
正确性靠什么判？同 SKU、bbox、目标商品、实体 ID、字段标签或外部知识。
数据是否真的提供这个 gold？“相关”不够，必须存在可执行、可评分的监督结构。
会不会产生伪捷径？近重复图、同源派生、类别泄漏和模板记忆都要控制。
缺失部分由谁补？资产/KB 补事实，TaskSpec 补语义，Codex 只补表达与组合。
能力最小监督信号仅有图片分类标签为什么不够核心评测对象
Exact Match稳定商品/SKU 身份 + 真实跨视角图类别相同不代表同一商品能否找回同一商品且不被近邻款干扰
Multi Search场景级多物体 bbox + 每个物体的 SKU/参考图只能知道“有杯子”，不能知道是哪一个杯子分解、逐物体检索和结果覆盖
Style Recommendation参考图 + 相对语言/偏好 + 目标候选同类商品不是风格兼容或偏好 gold约束理解、候选相关性与解释
Encyclopedia视觉实体身份 + 可核验知识来源类别名不足以支撑属性与知识陈述识别、证据引用与不编造
Document Reading文本框/转写 + 字段级 KIE 标签文档类型分类不能回答金额、日期、商户字段正确性、覆盖率和格式契约
Recipe Guidance菜品实体 + 经核验的配方/步骤知识识别“宫保鸡丁”不等于知道可靠做法识别、知识落地和安全边界
选择原则：公开数据不是按“场景相似度”堆叠，而是按“监督信号互补性”组合。每个来源都要有清晰角色，也要写清楚它不能被用于证明什么。
04 · Six capability portfolios

六项能力如何落到具体数据源

Core r3 的 1,500 条轨迹实际引用 8 个公开图像来源。下面不仅列“用了什么”，还解释“为什么它能提供正确的监督信号”以及“哪里必须补第二层证据”。

Exact Match · 375 条

同一商品检索

ABO · 375 exact-match query bindings
商品/Listing 身份真实多视角query-gallery 隔离

为什么选：Amazon Berkeley Objects 提供稳定商品身份和多视角商品图，能够把“同类”与“同一商品”区分开。

关键控制：禁止把简单裁剪、缩放或近重复图当成正样本；同一商品家族必须在切分时保持原子性。

Multi Search · 225 条

多商品场景检索

RPC · 225 query bindings
多物体场景bbox逐物体 SKU

为什么选：Retail Product Checkout 同时有拥挤零售场景、物体框与商品级身份，支持先分解、再逐项检索。

反例：COCO 虽有 bbox，但只能提供通用物体类别，无法定义电商 SKU 检索的 gold。

Style Recommendation · 300 条

发散式风格推荐

FashionIQ · 272 / ABO · 28 query bindings
参考图相对语言目标候选

为什么选：FashionIQ 的“参考图 + 修改描述 + 目标图”天然对应“更正式一点、换成短袖”等相对偏好；ABO 补充非服饰/家居风格。

反例：DeepFashion 可做服装候选库或同款排除，但类别/属性标签本身不是用户偏好或兼容性 gold。

Visual Encyclopedia · 300 条

视觉百科问答

iNaturalist · 262 / ABO · 28 / ISIA Food-500 · 10 query bindings
细粒度实体实体映射外部知识证据

为什么选：iNaturalist 提供细粒度物种身份，适合测视觉识别边界；少量商品和食物资产构成跨意图挑战。实体描述必须再绑定经过核验的知识来源。

边界：图片标签只负责“它是什么”，百科事实必须来自独立证据，不能由 Codex 或视觉分类标签自由发挥。

Document Reading · 90 条

票据与文档读取

CORD · 33 / SROIE · 27 / Wikimedia Documents · 30 query bindings
OCR 转写字段标签版面变化

为什么选：CORD 和 SROIE 提供收据文本/字段结构，可验证商户、日期、总额等答案；Wikimedia 文档补充非收据版面。

任务本质：这里评测的是 OCR/KIE 与输出契约，不是“这是不是一张收据”的分类。

Recipe Guidance · 210 条

看图做菜指导

ISIA Food-500 · 210 query bindings + reviewed recipe KB
菜品实体别名归一配方知识分离

为什么选：ISIA Food-500 提供中餐细粒度识别；实体/别名映射再连接到审核过的菜谱知识，形成“识别 → 检索 → 指导”。

边界：Food-500 不能独自证明食材用量或步骤正确，菜谱事实不能由图像类别标签推导。

为什么有些“看起来相关”的数据没有被当作 gold

候选来源可承担的角色不能承担的角色判断依据
MUGE / MEP-3M中文电商表达或困难负例参考Exact Match 正样本缺少稳定 SKU 的真实跨视角配对
COCO通用多物体视觉研究多商品 SKU 检索 goldbbox 后仍只有类别身份
DeepFashion服装候选、属性或同款排除风格偏好/相对推荐 gold类别相似不等于偏好匹配

05 · Four-layer composition

数据不是“混合”，而是四层职责分离

最重要的设计是把语义、事实、表达和接收权分开。Codex 不是事实来源，也不决定样本属于哪个 split；它只在已经冻结的约束内组织自然语言交互。

L1 · SEMANTIC

TaskSpec / Authoring Plan
规定 intent、capability、边界类型、交互形态、split、资产、顺序和稳定 ID。

语义权威
不是自然语言作者
L2 · FACTUAL

公开视觉资产 + verified KB
提供商品身份、bbox、目标候选、实体、OCR 字段、菜谱证据等可核验事实。

事实权威
不提供完整用户表达
L3 · PATTERN

DuRecDial / CrossWOZ / MUGE 等模式参考
抽取偏好追问、约束修正、无结果放宽、目标变化、短口语等交互模式。

形态权威
不提供业务 gold
L4 · COMPOSER

Codex
读取计划与可见资产，在有限字段内把事实和模式组合成自然、具差异性的单轮或三轮轨迹。

合成器
无权改标签、事实或 split
Codex 可以做
  • 让同一任务出现简短、口语、错别字、夹杂数字等表达差异；
  • 把预设的澄清、纠正、放宽或目标变化写成自然对话；
  • 在真实图片与冻结事实范围内选择合理指代；
  • 只返回 plan_id 与 turns。
Codex 不可以做
  • 新增/删除样本、移动 split 或改 capability；
  • 发明商品、文档字段、物种属性或配方事实；
  • 复制来源数据中的原始用户话术；
  • 自行把 staging 语料变成 accepted 语料。
最适合面试的表述：TaskSpec 是“语义真值”，公开资产与知识库是“事实真值”，对话数据只提供“交互先验”，Codex 是受限 composer，人类是最终 approver。
06 · Codex trajectory synthesis

Codex 如何合成“像人说话”的轨迹

合成并不是一句“大模型请生成 200 条问句”。它被拆成确定性计划与受控语言生成两部分：代码先锁定不可变字段，Codex 再补有限的自然语言表面。

07 · Human approval & immutable ledgers

人工审批不是“看几眼”，而是改变数据状态的唯一权限

机器检查回答“格式和契约是否成立”，人工审批回答“这条交互是否真实、事实是否可信、边界是否合理、是否可以成为评测资产”。两者不能互相替代。

批次级审批 · dev_mini

8 × 25 = 200

200 条 Phase 3 轨迹分 8 批生成。每批只有在通过质量检查、owner 逐条检查图文对应与话术可接受性，并显式 ACCEPT 后，才进入 accepted ledger。

可复核信号：当前 accepted 下有 8 个最终批次；另保留 4 个未被采用的早期 revision，说明 gate 不是自动盖章。

冻结分布：五 intent 为 35 / 35 / 35 / 35 / 60；六 capability 为 35 / 35 / 35 / 35 / 30 / 30；40 条 boundary，188 条单轮、12 条三轮澄清。

扩量后审批 · Core r3

自动守卫 + 定向 owner audit

扩量到 1,500 后，不再假装逐条人工生成。60 个计划批次先由冻结规则与机器校验控制，状态明确为 auto_approved_usable_pending_sample_review；随后从全量做覆盖 60 个生成批次和 12 个 prompt recipe 的 cluster-aware audit，得到 196 pass / 4 needs-revision。r3 再对 248 条 ASCII 语言问题与 2 条列表风格问题做 create-only 修订。

最终 receipt：从 250 条修订中按 10 个批次各抽 20 条，并强制覆盖 6 个已知修复点，共 200 pass / 0 needs-revision / 0 reject；corpus_status=approved，审核阶段模型调用为 0。

人工具体检查什么

FACT

事实与图像一致

指代对象确实可见；商品/字段/实体/菜谱信息不超出资产或 KB。

INTENT

意图与边界成立

用户话术能触发目标 capability；澄清样本真的有歧义，边界不过度造作。

LANGUAGE

自然但不模板化

口语、残句、修正合理；避免批次内机械换词和不符合中文习惯的翻译腔。

CONTRACT

轮次与角色合法

plan_id 对齐，单轮/三轮结构正确，assistant 只在需要追问时出现。

SAFETY

敏感与越界受控

不引入私人信息、凭据或不必要风险；Utility 不制造医疗等未实现主张。

PROVENANCE

来源声明诚实

明确 synthetic_derived；不复制源对话，不把合成样本称为真实用户日志。

状态机

plan → generated → staged → inspected → ACCEPT → accepted ledger

任何自动生成或质量检查都不能跨过人工接受节点。

不可变性

accepted 不做原地修改。发现问题时创建新 revision；历史候选、reviewer、时间、哈希和决定继续保留。

人工审核的准确含义intent、capability、boundary 与 split 由冻结 plan 拥有；owner 审的是图片—话术一致性、自然度、边界可接受性和是否进入 corpus，不是重新人工标注这四个字段。当前只有单 owner reviewer，因此不报告 inter-rater agreement。
面试里的工程亮点：我把“人工检查”做成了数据状态机，而不是文档约定。人类的决定有明确输入、输出、记录和不可变历史，因此失败 revision 能被复盘。
08 · Scaling: 200 → 1,500

09 · Split integrity & leakage control

同一张图换个问法，不能算两个独立样本

视觉 Agent 数据最容易发生的泄漏，不只是文本重复；同一商品、同一原图的裁剪、同一资产的多意图问法，都可能让测试集看起来更好。因此切分单位必须从“query 行”提升到“泄漏连通分量”。

原子切分规则

867 个 connected components

把共享源资产、商品身份、派生图或同图跨意图关系连接成 leakage group；整个 group 只能落入同一个 split。

刻意的跨意图挑战

38 组 / 104 条 query

同一图片会被问检索、推荐或百科等不同问题，用于测路由是否读懂意图；这些 query 作为一个原子组切分，不跨 train/test。

风险表面上看实际控制
同 SKU 多视角不同图片按商品/Listing 身份聚组，禁止跨 split
裁剪/派生图文件哈希不同追溯 source asset 与 derivative lineage
同图跨意图文本和标签都不同共享 asset 的 query 构成同一 connected component
模板近重复换了实体和少量词模板族、表达风格和交互形态按计划控制并做重复检查
合成器记忆语言自然冻结 split/ID/事实，Codex 无权选择测试位置或更改 gold
为什么这对 Skill 自进化尤其重要S1/S2/S3 会从失败轨迹中学习。如果同资产的另一种表达偷偷进入 holdout，系统可能只是记住对象或模板，而不是学会更好的 Skill。按 connected component 切分，才能让前后比较更可信。
10 · Interview scripts

把复杂设计讲成三种长度

先讲“为什么这样做”，再讲数据名。面试官如果追问，再进入监督信号、审批状态机和泄漏控制。

ONE SENTENCE · 10 SEC
我从论文五类电商视觉意图出发，把它们操作化成六项可评测能力，再按每项能力需要的监督信号组合 8 个公开数据源，用冻结 TaskSpec 和真实资产约束 Codex 合成交互轨迹，最后通过人工审批与泄漏分组形成 1,500 条可复核数据。
ELEVATOR PITCH · 30 SEC
数据部分的难点不是缺图片，而是论文意图没有直接对应的公开数据。我先把 Exact Match、Multi-Product、Divergent Recommendation、Encyclopedia 和 Utility 拆成六个有明确 gold 的 capability，然后按监督信号选数据：比如 ABO 提供同 SKU 多视角，RPC 提供多物体框和 SKU，FashionIQ 提供参考图加相对偏好，CORD/SROIE 提供字段级标签。真实数据负责事实，TaskSpec 负责意图，Codex 只负责把交互模式写成自然轨迹，人类保留最终接收权。这样得到的数据既贴近业务交互，又不会把模型生成内容误当成事实。
DEEP DIVE · 2 MIN
我先读论文的任务定义，而不是先搜“大而全”的电商数据集。论文有五类视觉意图，但它们是业务概念，所以我先做 operationalization：定义每类的输入、目标工具、输出契约和可评分 gold。Utility 里文档 OCR 和菜谱指导依赖完全不同的工具与证据，因此拆成两个 capability，最终是五类意图、六项能力。

接着我按监督信号选源。Exact Match 必须有稳定 SKU 和真实跨视角，所以用 ABO，而不是只有图文对的 MUGE；Multi Search 要同时有场景 bbox 和商品身份，所以用 RPC，而不是只有通用类别的 COCO；风格推荐用 FashionIQ 的参考图、相对语言和目标图；百科用 iNaturalist 的细粒度实体再连接知识证据；文档用 CORD/SROIE 的 OCR/KIE 标签；菜谱把 Food-500 的菜品识别与审核过的菜谱知识分开。

在合成层，我把数据职责拆成四层：TaskSpec 决定语义，公开资产和 KB 决定事实，公开对话数据只贡献澄清、约束修正、目标变化等交互模式，Codex 只能在冻结计划中补自然语言。它不能改 capability、split、图片或 gold，每次严格生成 25 条 plan_id 对齐的单轮/三轮轨迹。dev_mini 的 8 个批次都经过显式人工接受，失败 revision 保留；扩量到 Core 后用自动守卫控制 60 个批次，再对 r3 修订语料做 owner audit。最后按 867 个 leakage connected component 切分同商品、派生图和同图跨意图样本，避免自进化系统从 holdout 偷看相近资产。
叙述顺序建议先说“监督信号优先”和“四层职责分离”，这两个是设计思想；再用 ABO/RPC/FashionIQ 举三个直观例子；最后用“人工 gate + connected component”收束工程可信度。
11 · Interviewer Q&A

面试官最可能追问什么

Q1：为什么不直接找一个大型电商多模态数据集？
因为六项能力需要的 gold 结构不同：同款检索要 SKU 多视角，多商品检索要 bbox + SKU，推荐要相对偏好，文档要字段标签。一个大数据集即使图片多，也很难同时提供这些监督。我的方案是按监督信号组合来源，并给每个来源定义允许与禁止用途。
Q2：Codex 会不会幻觉，污染事实？
它被限制在 composer 角色。intent、capability、split、image、boundary 和 gold 都由确定性计划与资产/KB 冻结；Codex 只输出 plan_id 和 turns。机器检查之后仍是 staging，必须人工接受。百科、文档、菜谱等事实也不能由模型自由补全。
Q3：这些轨迹真的“像人类”吗？
更准确的说法是“覆盖了受控的人类交互现象”，而不是“等同真实线上分布”。我们显式设计直接请求、澄清、约束修正、无结果放宽、目标变化，以及口语、残句、错别字/ASR、中英或数字混写。它适合机制级评测，但不能证明生产流量外部有效性。
Q4：人工审核 1,500 条是不是成本很高？
采用两层策略。dev_mini 阶段逐批显式接受，先把 authoring contract 校准；Core 扩量依靠冻结计划和自动守卫，不宣称逐条人工编写。首轮从全量 1,500 条分层抽 200 条并定位 4 条需修订；r3 对 248 条 ASCII 问题和 2 条风格问题做 create-only 修订，再按每个修订批次抽 20 条、强制覆盖已知修复点，共审核 200 条并形成可追溯 receipt。
Q5：为什么 Exact Match 用 ABO，不用图文检索数据？
Exact Match 的正样本定义是“同一商品”，不是“语义相关”。ABO 有稳定 listing/product 身份和真实多视角；很多图文检索数据只有描述相关性，无法证明两张图属于同一 SKU，因此可做语言或负例参考，却不能做正样本 gold。
Q6：Food-500 有类别，为什么还要菜谱知识库？
视觉类别只回答“这是什么菜”，不能回答“需要哪些材料、按什么步骤做”。因此把识别与知识分开：Food-500 锚定菜品实体，经审核的别名映射连接到 recipe KB，回答必须落到该证据；这能避免模型从菜名直接编步骤。
Q7：同一图片用于多个意图，是数据重复吗？
这是刻意设计的路由挑战：同一图既可被问“帮我找同款”，也可被问“这是什么/适合什么风格”。它测试系统是否理解用户意图而不是看图猜 skill。为了不泄漏，共享图片的 query 会被归入同一个 leakage component，只落在一个 split。
Q8：这部分最能体现你的算法能力还是工程能力？
两者都有。算法上是把业务意图转换为监督结构、分布轴和泄漏图；工程上是实现确定性 plan、固定批次合成、guard、staging/accepted 状态机、hash/ledger 与 create-only revision。它为后续 Skill 自进化提供了可信训练/优化/保留集边界。
Q9：你说用了 Codex 5.6 Sol Ultra，证据强度是什么？
manifest 记录 provider=codex 和该显示名，但模型身份来自当时的用户确认，不是 provider-attested request metadata。因此可以描述“按用户确认记录的模型显示名”，不能声称掌握 served revision、provider request ID 或底层重试细节。
不要这样说“我混了几个开源数据集，让 Codex 模拟真实用户，所以构建了生产级数据。”更准确的是：“我用公开资产构造了覆盖真实任务语义的机制级评测数据，并用受控合成恢复交互形态；其生产分布外部有效性仍需线上数据验证。”
